# MVP backlog: разработка через TDD

Цель MVP — проверить, станет ли голосовой Telegram-бот самым быстрым и надёжным способом создать личное напоминание.

## Как работаем

Для каждого вертикального среза повторяем короткий цикл:

1. **Red** — описываем ожидаемое поведение тестом и видим осмысленное падение.
2. **Green** — добавляем минимальную реализацию, необходимую для прохождения теста.
3. **Refactor** — улучшаем структуру без изменения поведения.
4. Запускаем все тесты, чтобы не допустить регрессий.

Срез считается готовым, когда поведение покрыто автоматическими тестами, полная сборка проходит локально и тот же набор проверок может выполнить GitHub Actions.

## Порядок срезов

### 1. Сервис напоминаний

Пользователь может создать напоминание на будущее, завершить его или перенести. Система запрещает пустой текст, время в прошлом и некорректные переходы состояния.

Реализуем привычными слоями Spring MVC: `controller → service → repository → PostgreSQL`. Бизнес-сценарии проверяем быстрыми unit-тестами `ReminderService` с Mockito, веб-контракт — `MockMvc`, хранение — JPA-тестами с Testcontainers.

### 2. Хранение напоминаний

Напоминание сохраняется в PostgreSQL и восстанавливается без потери состояния. Схема создаётся версионируемой миграцией Flyway.

Проверяем repository-интеграционными тестами с Testcontainers.

### 3. Доставка без дублей

Наступившие напоминания выбираются для отправки. Повторный запуск воркера или временный сбой не создаёт две одинаковые доставки.

Сначала атомарно создаём durable outbox-запись с уникальным `reminder_id`. Повторный запуск безопасен на уровне PostgreSQL. Отдельный sender затем доставляет pending-записи через Telegram и фиксирует результат.

Проверяем полным Spring integration-тестом с настоящим PostgreSQL, управляемыми часами и повторным запуском enqueue.

### 4. Текстовый сценарий Telegram

Пользователь отправляет текст вроде «завтра в 15:00 покормить кота», подтверждает распознанные данные и получает напоминание в нужное время.

Сначала используем локальный адаптер и записанные Telegram Update fixtures, без реального webhook.

### 5. Голосовой сценарий

Бот принимает голосовое сообщение, получает аудиофайл и передаёт распознанный текст в тот же сценарий, что и обычное сообщение.

Bot API отдаёт `file_id` голосового сообщения, а не готовый текст. Бот скачивает OGG/Opus и отправляет его внешнему speech-to-text провайдеру. Сначала используем mock провайдера в тестах, затем реальную интеграцию.

### 6. Разбор намерения и неоднозначности

Из текста извлекаются действие, дата, время и часовой пояс. Если данных не хватает, бот задаёт уточняющий вопрос, а не угадывает молча.

Проверяем набором разговорных фраз и пограничных дат.

### 7. Полный диалог управления

Кнопки «Готово», «Перенести» и «Отменить» изменяют состояние напоминания. Повторное нажатие безопасно.

Проверяем сценарными тестами без сети.

### 8. Реальные интеграции

Подключаем Telegram webhook, провайдера транскрибации и модель разбора текста. Контракты ядра при этом не меняются.

Проверяем контрактными тестами и минимальным smoke-тестом тестового бота.

### 9. Эксплуатация и приватность MVP

Добавляем метрики доставки, структурированные логи без содержимого личных сообщений, обработку повторных webhook и удаление пользовательских данных.

## Критерий готовности MVP

MVP готов к закрытому тесту, когда пользователь может голосом создать однократное напоминание, увидеть и подтвердить правильную интерпретацию, получить его не раньше и не позже допустимого окна, а затем завершить или перенести. Повторы запросов и перезапуск приложения не должны терять или дублировать напоминания.
