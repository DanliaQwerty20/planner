# Проверка голосовых сценариев

Цель этапа — проверить не привлекательность идеи, а реальное поведение людей и разнообразие их естественных формулировок.

## 1. Выбор участников

Найти 5–10 человек, которые используют хотя бы два из трёх способов:

- «Сохранённые сообщения» Telegram;
- голосовые сообщения самому себе или другим;
- будильники для напоминания о делах.

Желательно включить людей с разными режимами жизни: работа по расписанию, свободный график, учёба, семья и бытовые обязанности.

## 2. Задание участнику

Текст приглашения:

> В течение недели, когда ты захочешь что-то не забыть, запиши это обычным голосовым так, как сказал бы личному помощнику. Не старайся говорить правильно или называть точную дату специально. Если есть личные данные, можешь заменить имена. После голосового напиши, когда и как ты хотел бы получить напоминание.

Не нужно заранее объяснять участнику поддерживаемые команды — иначе формулировки станут искусственными.

## 3. Карточка разбора одного сообщения

Для каждого примера заполнить:

| Поле | Значение |
|---|---|
| Код примера | Например, V001 |
| Дословная расшифровка | Что сказал пользователь |
| Ожидаемое действие | Что должно произойти |
| Тип | Напоминание / событие / гибкая задача / заметка |
| Дата | Явная, относительная, отсутствует |
| Время | Точное, приблизительное, отсутствует |
| Повторение | Нет или правило повторения |
| Количество намерений | Одно или несколько |
| Нужен уточняющий вопрос | Какой именно |
| Желаемая настойчивость | Один раз / до подтверждения / пользователь не уверен |
| Возможное автоматическое действие | Что ассистент мог бы подготовить или сделать |
| Цена ошибки | Низкая / средняя / высокая |
| Личные данные | Есть / нет; какие данные нужно скрыть |

## 4. Вопросы сразу после примера

- Почему вы не создали обычное напоминание или событие календаря?
- Что вы сделали бы с этой мыслью сейчас без ассистента?
- Какой ответ ассистента был бы достаточным?
- Нужно ли подтверждение или оно раздражает?
- Что должно произойти, если вы не отреагировали на напоминание?
- Разрешили бы вы ассистенту подготовить или выполнить часть действия?

## 5. Итоговые вопросы после недели

- Сколько раз вы вспомнили о деле, но не записали голосовое, и почему?
- В каких ситуациях говорить было неудобно?
- Какие запросы казались слишком личными?
- Где текст оказался удобнее голоса?
- Какие напоминания вы проигнорировали бы?
- Чего не хватило бы для ежедневного использования?
- Стали бы вы искать замену, если бы сервис исчез?
- За что именно вы потенциально согласились бы платить?

## 6. Что считать сильным сигналом

- участники присылают реальные, а не придуманные запросы;
- один человек создаёт три и более запроса в неделю;
- встречаются запросы, которые неудобно оформить будильником;
- участники самостоятельно начинают использовать несколько дел в одном голосовом;
- люди хотят переносить или исправлять задачи тоже голосом;
- после недели участник продолжает присылать запросы без дополнительного напоминания;
- существующие решения не справляются с повторяющимся классом формулировок.

## 7. Что считать слабым сигналом

- люди хвалят идею, но не могут привести реальный пример;
- все запросы сводятся к простым таймерам на несколько минут;
- участники предпочитают системного голосового помощника;
- голос используется только ради эксперимента;
- большинство задач не требует возвращения в определённый момент;
- необходимость подтверждать распознавание делает процесс дольше будильника.

## 8. Решение после сбора примеров

По завершении исследования:

1. Сгруппировать запросы по типам.
2. Выделить десять наиболее частых языковых конструкций.
3. Определить обязательные уточняющие вопросы.
4. Оценить цену ошибки для каждого класса.
5. Скорректировать границы MVP.
6. Только после этого выбрать архитектуру и создать технический прототип.
